# Changelog

Format basé sur [Keep a Changelog](https://keepachangelog.com/fr/1.1.0/), versions au format [SemVer](https://semver.org/lang/fr/).

## [Unreleased]

### Added

- Une pression plus courte qu'une image (un toucher très bref sur un appareil lent, ou `adb shell input tap`) n'était jamais vue par le jeu : le bouton montait avant que la simulation le lise. Le bouton reste maintenant enfoncé pendant un tick, puis se relâche à l'image suivante (`run_loop`). Le tower defense range aussi sa barre du bas dans 600 pixels de large (la forme la plus étroite qu'il prend), pour que rien ne soit coupé sur un téléphone tenu droit. Sur Android, la fenêtre est maintenant vraiment plein écran (`SDL_WINDOW_FULLSCREEN`) : la barre d'état restait affichée, la fenêtre était 24 pixels plus courte que l'écran et recouvrait le haut du jeu ; un toucher visé sur l'écran tombait donc à côté. Le script de l'émulateur écrit, quand un toucher ne change rien, l'état du système et un balayage de touchers.

- ADR 0013, G11 : les trois jeux d'essai (`game_2048`, `chess`, `tower_defense`) entrent dans la CI et la release. Job `export` : zips Windows et Linux vérifiés ; job `android-export` : vrai export Android puis jeu dans l'émulateur par des touchers (une pièce choisie puis jouée, une tour construite puis la vague suivante) et des glissés (2048) ; release : zips et APK des six jeux. `platform/android/run_game_on_device.sh` apprend `GAME_TOUCHES` et `GAME_SWIPES` (chaque toucher doit changer l'écran), `spike/pixel.py differs` compare deux captures.

- ADR 0013, G10 : le jeu **`games/tower_defense`**, sans C++ : une route, quatre tours (canon, mortier, glace, sniper) à trois niveaux qu'on construit, améliore et vend avec l'or des monstres, quatre monstres, douze vagues dont un chef, victoire et défaite, nouvelle partie. Touche ou clic sur une case pour construire, sur une tour pour la sélectionner ; boutons de la boutique, touches 1 à 4 et espace. 22 scénarios, `docs/GAME_TOWER_DEFENSE.md`. Corrigé en chemin : `health::deal` perdait une demande de dégâts quand deux sources frappaient la même entité dans le même tick (un test de `health` le couvre).

- ADR 0013, G9b : quatre modules pour le tower defense, sans un mot de tower defense dans leur code. `path2d` (`Waypoint` : un point d'un chemin ; `PathFollower` : avance le long d'un chemin à une vitesse qu'un ralentissement ou le réglage `speed_scale` modifient, blesse une cible étiquetée au bout, lève une action et disparaît), `autofire` (`AutoFire` : tire un projectile vers une cible à portée, le plus proche, le premier, le dernier, le plus solide ou le plus faible, sur des couches voulues), `waves` (`WaveGroup`, `WaveController` : des vagues décrites par des groupes de N choses à intervalle régulier, finies quand plus rien n'appartient à la vague, `all_cleared` une seule fois) et `economy` (`Wallet`, `Bounty`, `Upgradable`, `Sellable`, `Placer` : acheter sur une case libre, sélectionner, améliorer, vendre ; le `Placer` partage l'entité du `grid2d.GridCursor`). Tests de chaque module.

- ADR 0013, G9a : reprise de `combat2d`. Nouveau `health` (`Health` : des points de vie, `Damage` : une demande de dégâts que n'importe quelle source ajoute à une entité, `Dead` : l'entité est à zéro ; une action et la destruction facultatives), nouveau `bounds2d` (`OutOfView` : ce qui sort d'un côté de l'écran lève une action et/ou disparaît ; `ge/mod/bounds2d/edge.hpp` donne le bord de l'écran aux autres modules), `transform2d.SpeedScale` (un facteur de vitesse propre à une entité, qui s'use au bout de N ticks), et `combat2d` recentré sur les sources de dégâts : `ContactDamage` (toucher blesse, avec un délai de récupération) et `Projectile` (couches visées, dégâts de zone, traversée, poursuite, ralentissement de ce qu'il touche). **Changement qui casse les anciens fichiers de jeu** : `combat2d.Mortal` et `combat2d.Target` n'existent plus (remplacés par `health.Health` + `combat2d.ContactDamage` / `bounds2d.OutOfView`), et `spawner2d.Cull` non plus (`bounds2d.OutOfView`). `doodle_jump` et `sideways_jump` sont migrés, leurs scénarios passent sans modification.

- ADR 0013, G8 : le jeu **`games/chess`**, sans C++ : échecs complets à deux sur un écran (coups légaux montrés par des points et des anneaux, échec, mat, pat, roque des deux côtés, prise en passant, promotion au choix en dame, tour, fou ou cavalier, abandon, nouvelle partie) ; vingt-trois scénarios joués au pointeur. Pour lui, `grid2d.Zone` (un rectangle de cases qui voit arriver des entités, d'un genre donné s'il le faut, lève une action et garde un lien vers la première) et `rules.OnAction.link` (la cible est l'entité vers laquelle pointe un champ-lien de la source, par exemple la pièce vue par une zone). Voir `docs/GAME_CHESS.md`.

- ADR 0013, G7 : `turns` (`Turn` : le tour de jeu, `Team` : à quel joueur appartient une entité) et `grid_moves` : comment des pièces se déplacent sur une grille, en données. Chaque façon de se déplacer est une entité `Pattern` (glisseur ou sauteur, portée, direction, déplacement seul ou prise seule, premier coup seulement, case de passage non menacée, prise ailleurs que sur la case d'arrivée, second déplacement simultané) ; `Guard` marque ce qui ne doit pas rester menacé (un coup qui le laisserait menacé est illégal) ; `Side` donne en faits (menacé, plus aucun coup) l'état d'un camp ; `MoveRequest` est la seule porte d'entrée d'un coup ; `Picker` choisit un coup en touchant une pièce puis une case ; `Marker` montre la sélection, les coups possibles, le dernier coup et la menace. Le module ne connaît aucun jeu : ses tests jouent des pièces inventées sur un plateau de 5 par 5.

- ADR 0013, G6 : le module `slide_merge` (`SlideBoard` : tout un plateau de tuiles glisse d'un coup dans une direction, deux tuiles égales fusionnent une fois par coup, le score, la plus grande valeur, le nombre de coups, et l'action « bloqué » ; modes somme, valeur suivante ou sans fusion ; `Tile`) et le jeu **`games/game_2048`**, sans C++ : flèches, WASD/ZQSD ou glissé, deux tuiles au départ puis une par coup utile, victoire à 2048 avec « Continuer », fin de partie, nouvelle partie à tout moment (R, N, bouton), meilleur score gardé ; quinze scénarios. Voir `docs/GAME_2048.md`.

- ADR 0013, G3 et G5 : `grid2d` (`Grid` : un plateau de cases ; `GridPos` : la case d'une entité, avec glissement possible et prise de la case depuis la position ; `Blocked` ; `GridCursor` : la case sous la souris ou le doigt, lue à travers la caméra, et l'action d'un clic ; `SpawnOnEmpty` : créer des entités sur des cases libres tirées au hasard, avec un préfab rare) et `gesture` (`Swipe` : un glissé assez long et assez rapide lève l'action de sa direction, souris et doigt). `grid2d` offre à ses dépendants `ge/mod/grid2d/cells.hpp` (positions des cases, qui est sur quelle case) ; un module peut maintenant avoir un dossier `include/` pour cela.

- ADR 0013, G2 : trois modules et deux composants. `tween2d` (`Tween` : un nombre va d'une valeur à une autre en N ticks avec une courbe, après un délai, `Settle` : un nombre qui s'approche d'un but) anime n'importe quel champ numérique d'un composant, par son nom ; `rules` (`Watch` : lève une action quand un nombre entre dans un intervalle, `OnAction` : change un nombre quand une action est levée) ; `phase` (`Phase`, `Transition`, `ShowIn`, `ActiveIn` : les phases d'un jeu et ce qui s'y voit et s'y joue, sans changer de scène). `transform2d.Scale` (taille de dessin, lue par `sprite2d`, `text2d` et `debug_draw`) et `transform2d.Disabled` (l'entité est mise de côté). Chaque module généré a maintenant une fonction d'écriture d'un champ par son nom (`ComponentInfo::write`).

- Trois jeux pour éprouver le moteur (ADR 0013 : 2048, échecs, tower defense) ; premier jalon, G1, de petites extensions que les trois utilisent : `transform2d.Hidden` (ni dessinée ni cliquable : lu par `sprite2d`, `text2d`, `debug_draw` et les boutons de `ui`), `transform2d.Owner` (un lien vers l'entité qui en a créé une autre, posé par `SpawnRequests::spawn_owned`) et `transform2d.Attach` (suit son `Owner`, disparaît avec lui) ; `debug_draw.Rect`, `Circle` et `Line` (pleins ou en contour, avec transparence, dessinés par SDL) ; `camera2d.CameraFit` (le zoom et la position qui font tenir une zone du monde dans la fenêtre, marges pour l'interface) ; `sprite2d.FrameBind` (l'image vient d'un nombre de l'entité, en logarithme si on veut) ; `ui.Bind.own` (le texte ou la barre lit un nombre de sa propre entité). Nouveau : `Entity::to_link` et `from_link`.

- Jeu de référence `games/sideways_jump` : un Doodle Jump tourné d'un quart de tour (gravité vers la gauche, rebond sur le côté droit des blocs, caméra qui ne va qu'à droite, monde généré vers la droite, score à la distance), sans C++ ni image, avec huit scénarios. Il montre que les modules ne connaissent ni le haut ni le bas ; voir `docs/SIDEWAYS_JUMP.md`.

- Modules sans « haut » ni « bas » en dur : `camera2d.CameraFollow` gagne `offset_x`, `only_down`, `only_left` et `only_right` (comme `offset_y` et `only_up`) ; `bounce2d.Bouncer` et `combat2d.Mortal` gagnent `fall_x` et `fall_y`, le sens de la chute (par défaut vers le bas : rien ne change) : un jeu dont la gravité pointe vers la droite ou le haut rebondit sur le bon bord, une planche qui casse tombe dans le sens de la chute et `fall_death` surveille le bord d'écran de ce côté. Nouveau `include/ge/app/direction.hpp` pour lire un sens à partir de deux nombres.

- `scripts/setup_linux.sh` : installe sous Linux (Debian, Ubuntu, WSL) ce qu'il faut pour compiler et jouer, avec `--android` le JDK, le SDK et le NDK Android, avec `--dev` clang-format et clang-tidy ; relançable, `--dry-run` dit le plan. Un workflow `Setup script` l'exerce sur un Ubuntu vierge.

- Export Android (ADR 0012, A3) : `gectl export JEU --target android [--abi a,b]` fabrique un `.apk` (NDK pour `libmain.so`, Gradle pour l'APK, gabarit dans `platform/android/template/`) et dit ce qui manque (SDK, NDK, JDK, Ninja). La cible reste cachée jusqu'à A7. Un workflow `Android export` l'exerce pour de vrai sur un émulateur.

- Tactile (ADR 0012, A4) : les doigts arrivent en sources `touch:down/x/y` (jusqu'à cinq : `touch:down2`…), le premier est aussi une souris (un jeu souris se joue au doigt, compté une fois), les positions sont en pixels du jeu, le bouton Retour d'Android est `key:ac_back` et quitte comme Échap, un hôte mobile ignore les boutons « Quitter ».

- Module `touch_controls` (ADR 0012, A5) : `TouchButton`, `TouchStick` et `TouchKnob` dessinent des contrôles pour un écran tactile (cachés sur un ordinateur jusqu'au premier doigt) et donnent des actions au jeu ; joystick et bouton de tir pour `doodle_jump`, joystick pour `treasure_run` (avec un scénario chacun). Les positions des doigts sont des pixels, pas des axes.

- CI et release Android (ADR 0012, A6) : chaque pull request exporte `doodle_jump` et `treasure_run` en APK, lit le paquet avec `aapt2` puis le joue sur un émulateur (tape sur Jouer, doigt sur le joystick, Retour) ; la release ajoute les APK des jeux de référence. Nouvelle page `docs/EXPORT_ANDROID.md`.

- Export Android (ADR 0012, A7) : la cible `android` est proposée (`gectl export --targets` dit ce qui manque, le lanceur la liste) ; `--install` met l'APK sur le téléphone ou l'émulateur par `adb`, `--keystore` et `--key-alias` signent avec sa propre clé (mots de passe par l'environnement).

- Menus : `ui.Menu` lit ses boutons comme un tableau d'après leur place à l'écran. Nouvelles actions `left` et `right` : elles déplacent le focus le long d'une ligne de boutons côte à côte, `up` et `down` changent de ligne (vers le bouton le plus proche), grilles comprises. Le lanceur : flèches gauche/droite (ou A/D) naviguent, PageUp/PageDown tournent les pages.

- Lanceur : un petit bouton à l'icône d'export à droite de chaque jeu ouvre l'écran d'export de ce jeu (le bouton « Export » du bas disparaît). Nouveau composant `ui.RowButton`, un second bouton pour la rangée d'une liste paginée.

- Jeux adaptatifs : `"window": {"adapt": true}` fait suivre à la zone de dessin la forme de l'écran (le petit côté garde sa taille, le grand s'étire dans des limites), pour remplir tous les téléphones sans bandes ; `doodle_jump` s'adapte de 9:16 à 9:21. `Backend::adapt_view`/`view_size`/`set_window_size`, `Viewport` mise à jour à chaque image, `geplay --window LxH` pour essayer une forme d'écran sur un ordinateur.

### Changed

- CI et builds plus rapides. **ccache** est utilisé tout seul par CMake quand il est installé (`cmake/GeCompilerCache.cmake`, `-DGE_CCACHE=OFF` pour s'en passer ; `scripts/setup_linux.sh` l'installe) : un nouveau dossier de build, un changement de branche ou un export recompilent en secondes ce qui l'a déjà été, SDL compris. En CI, chaque job qui compile garde son cache (`.github/actions/ccache`), et un push sur `dev` relance le niveau des PR pour réchauffer ces caches (personne ne l'attend). Sous Windows, `gectl export`, `scripts\export.cmd` et `gameEngine.cmd` compilent sur tous les cœurs (`--parallel`, `UseMultiToolTask`) : MSBuild compilait les fichiers d'un projet un par un.

- Le module `altitude` devient `progress` : `progress.Progress` mesure jusqu'où une entité est allée dans un sens (`toward_x`, `toward_y` ; haut par défaut, droite pour un coureur, bas, gauche), sans compter les retours en arrière, et en tire un score entier. `Altitude` devient `Progress`, `height` `distance` et `origin_y` `origin`. `doodle_jump` est mis à jour.

- `spawner2d.Generator` ne pose plus ses rangées « vers le haut » : `toward_x` et `toward_y` donnent le sens (haut par défaut ; droite pour un coureur, bas, gauche), et `spawner2d.Cull` détruit ce qui sort du côté d'écran que disent `side_x` et `side_y` (bas par défaut). Les champs qui parlaient de hauteur ou de x et y en dur sont renommés : `x_min`/`x_max` deviennent `across_min`/`across_max` (en travers du sens), `next_y` `next`, `origin_y` `origin`, `ramp_height` `ramp_distance`, `from_height` `from_distance`, `extra_dx` `extra_across` et `extra_dy` `extra_along` (positif : en avant ; l'ancien `-14` s'écrit `14`). `across_max` vaut 0 par défaut (480 était la largeur de doodle_jump). `doodle_jump` est mis à jour et construit le même monde pour la même graine.

- Les fichiers d'un jeu exporté se lisent par SDL (`read_file`, `list_game_files`) et l'export écrit `data/files.txt` : de quoi lire dans un APK (ADR 0012, A2). `ge_add_player` crée la bibliothèque `main` sous Android.
- L'export est fait de deux étapes que chaque plateforme fournit (`ExportTarget::build` et `assemble`, ADR 0012, A1) ; Windows et Linux partagent une base `DesktopTarget`. Aucun changement pour un joueur.
- ADR 0012 : plan de l'export Android (APK) en huit jalons A0 à A7 ; `docs/ROADMAP.md` les liste.
- Windows : les chemins sont du UTF-8 (`ge/core/path.hpp`) : un jeu dans un dossier avec accent (`C:\Users\Léa\…`) trouve ses fichiers, ses sons, ses images et sa sauvegarde ; révélé par le job CI « Export ».
- CI : AddressSanitizer, clang-tidy et le build GCC Debug ne tournent plus en CI ; `scripts/check.sh` les exécute avant chaque pull request (le dépôt est public, mais ils doublaient ce que le script fait déjà).
- ADR 0011 : décisions du lanceur (un jeu en JSON avec un hôte mince) et de l'export autonome par plateforme ; `docs/ROADMAP.md` liste les étapes E0 à E7.
- Branches : `main` reste la dernière étape validée, les pull requests visent `dev`. La CI passe sur `dev` ; le workflow « Promote dev to main » avance `main` sur un commit de `dev` déjà vert et pose l'étiquette de version. Les issues « Module gap » et `ci-failure` (ouverte et fermée par un workflow) sont décrites dans `CONTRIBUTING.md`.

- M4 : scénarios de test dans les jeux (`scenarios/*.json` : ticks, entrées scriptées, vérifications comme `hero.transform2d.Position.x > 100`), validés par `gectl validate` ; `gerun --test [--scenario NOM]` les exécute, chacun deux fois pour contrôler le déterminisme ; schéma éditeur des scénarios ; jeux de référence `sparks` et `pilot` testés en CI.
- M4 : chaque composant généré a une fonction `read` (lecture d'un champ par son nom) ; rendu nul (`NullRenderer`) et enregistreur (`RecordingRenderer`) ; le moteur est compilé avec `-ffp-contract=off`. Documentation : `docs/TESTING.md`, ADR 0005.

- M5 : `gectl new-module NOM [--depends A,B]` crée un module qui compile et passe son test ; CMake découvre les modules (`modules/*/module.json`) et leurs tests (`modules/<nom>/tests/`), `gerun` les lie tous : ajouter un module ne modifie aucun fichier CMake.
